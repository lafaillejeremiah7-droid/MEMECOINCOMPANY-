# NQ order flow signal bot with self-adaptation

A new `orderflow/` package (14 Python modules, ~3,600 lines) that connects to IB Gateway via ib_insync in read-only mode and computes real-time order flow metrics—cumulative delta, volume profile, DOM analysis, large prints, absorption—to generate advisory trading signals for NQ futures. A self-adaptation engine tracks forward results per signal type and automatically disables underperformers (WR < 50% over 30 signals) or re-enables recoverers (WR > 55% over 20 signals). Signals are persisted in SQLite via aiosqlite and pushed to Telegram with hourly/daily/weekly reports. The entire system is signal-only and never places orders.

**Watch for:** The aggressor-side classification is hardcoded to `is_ask = True` (confirmed), which means cumulative delta, absorption, and large-print directionality are meaningless in production. The forward-results updater (`_check_forward_results`) is a no-op stub (confirmed), so the adaptation engine can never compute win rates from live data and will never disable or re-enable any signal. Bars are never closed in the main loop (confirmed), so delta divergence detection—which requires populated `self.bars`—cannot fire.

**Verdict**: NEEDS_CHANGES

## High-level view

The architecture is cleanly modular: each computation (delta, DOM, volume profile, absorption, large prints) lives in its own file with a detector class, a signal dataclass, and a method that the main orchestrator calls per tick or per DOM update. The signal engine applies cooldowns and enable/disable state before emitting, and the adaptation engine sits on top of the database layer to evaluate rolling performance. The design is sound; the issue is that three critical data paths are stubbed or broken.

The entire order flow analysis pipeline depends on correctly classifying each trade as buyer- or seller-initiated. The `_on_tick` handler hardcodes `is_ask = True`, making every trade look like a buy. Delta will only accumulate positive, absorption will only detect "buying absorbed" (SHORT signals), and large-print clusters will only fire in the LONG direction.

The self-adaptation engine is fully wired—database schema, rolling-window queries, disable/enable logic—but the forward-results loop that feeds it real outcomes is an empty `pass` statement. Without forward results, `get_rolling_win_rate` will always return `(0.0, 0)` and no adaptation action will ever trigger.

Delta divergence detection requires bars to be present in `self.bars`, which only happens when `close_bar()` is called. The main loop never calls it, and there is no timer or bar-boundary logic to trigger bar closure. The divergence detector will never see enough bars to reach the lookback threshold.

The read-only safety posture is well enforced: `readonly=True` is passed to `connectAsync`, the config validator rejects `readonly: false`, and grep confirms no order-placement calls exist in the package. The test suite (98 tests) validates each computation module in isolation but does not exercise the main orchestration loop or the integration between modules—so the three integration bugs above were not caught.

1. **Aggressor side always `True`** — `_on_tick` hardcodes `is_ask = True` instead of reading the tick's exchange-provided aggressor flag. All directional computations (delta, absorption direction, large-print direction) will be wrong. Parse `ticker.tickByTicks` or compare trade price to `ticker.bid`/`ticker.ask` to extract the actual aggressor side. (confirmed)
2. **Forward results never populated** — `_check_forward_results` is a `pass` stub. The adaptation engine cannot compute win rates. Implement the loop: query `get_signals_without_results()`, compare current price against `entry_price` at the elapsed intervals, call `update_forward_result()`. (confirmed)
3. **Bars never closed** — `close_bar()` is never called in the main loop. Delta divergence detection requires populated bars. Add a 5-second (or configurable) timer that calls `self.delta.close_bar(timestamp)` periodically. (confirmed)
4. **Reconnection fires in sync context** — `_on_disconnected` calls `asyncio.ensure_future(self._reconnect())` from an ib_insync event callback. If the event fires outside the running loop (during shutdown race), this will raise `RuntimeError: no current event loop`. Wrap in a try/except or use `loop.call_soon_threadsafe`. (likely)
5. **Absorption priority undocumented** — If both sell and buy volume exceed `min_volume` at the same level, only the sell-absorption branch fires (LONG) because `_reset_level` clears state before the buy check. The implicit priority could produce confusing behavior at heavily contested levels. Document or make explicit. (possible)

## Aggressor-side hardcoding renders delta meaningless

In `main.py` line 214:

```python
is_ask = True  # Default; in live IB, this comes from tick attributes
```

This is the single value that flows into every downstream computation. The `reqTickByTickData` call in `connection.py` requests `"AllLast"` ticks, which means ib_insync will deliver `TickByTickAllLast` objects. The ib_insync `TickByTickAllLast` namedtuple has no direct `side` field—determining aggressor requires comparing the tick price to the current bid/ask spread (if price >= ask, buyer-initiated; if price <= bid, seller-initiated). This logic needs to be implemented using the most recent `ticker.bid` and `ticker.ask` values, which are available on the Ticker object.

Without this fix, cumulative delta will only increase, absorption will only detect SHORT signals (buying being "absorbed"), and large-print clusters will only fire LONG.

## Forward-results stub breaks the adaptation feedback loop

```python
async def _check_forward_results(self) -> None:
    # This would normally check current price against past signal prices
    # In production, this runs periodically to update the forward results table
    pass
```

The adaptation engine's `evaluate_signal_performance` queries `get_rolling_win_rate`, which joins `signals` to `forward_results` filtering on `result_15m IS NOT NULL`. Since no code ever inserts rows into `forward_results`, the query always returns zero rows. The disable/re-enable logic gates on `sample_count >= self.rolling_window` (30), so it can never trigger.

The implementation needs to: (1) call `get_signals_without_results()` to find signals older than their interval thresholds, (2) get the current price, and (3) call `update_forward_result`. A complication: the 5-minute check needs the price *at t+5m*, not the current price at an arbitrary later time. This requires either a scheduler that wakes at t+5m/15m/30m/1h for each signal, or a periodic scan that checks elapsed time and records current price at the appropriate moment.

## Bars never close—divergence detection cannot fire

`CumulativeDelta.detect_divergence` returns `None` if `len(self.bars) < self.lookback` (default 10). Bars are only added via `close_bar()`. The main orchestrator calls `update_tick()` per tick but never calls `close_bar()`. The `self.bars` deque stays empty.

Fix: add a periodic bar-close timer in the main loop:

```python
if (now - last_bar_close).total_seconds() >= 5:
    self.delta.close_bar(now)
    last_bar_close = now
```

## Reconnection event-loop safety

`connection.py` registers `_on_disconnected` via `self.ib.disconnectedEvent`. The ib_insync library may invoke this callback after the event loop has stopped during shutdown. The handler calls `asyncio.ensure_future(self._reconnect())`, which requires a running event loop.

The `shutting_down` flag provides partial protection, but the `ensure_future` call itself can fail before `_reconnect` checks that flag:

```python
def _on_disconnected(self) -> None:
    self.connected = False
    if not self.shutting_down:
        try:
            asyncio.ensure_future(self._reconnect())
        except RuntimeError:
            pass  # Loop already closed
```

## Test coverage gaps

Not tested: the main orchestrator loop (`OrderFlowBot.start`, `_on_tick`, `_process_tick_signals`, `_check_scheduled_reports`), the integration between connection callbacks and computation modules, the Telegram `send_message_async` function, config validation rejection paths, and the entire `connection.py` module (reconnection logic, signal handlers, data subscription flows). The three blocking bugs above are all integration-level issues that unit tests on individual modules did not surface.

## Absorption double-trigger edge case

In `_check_absorption`, both the sell-volume and buy-volume branches are checked sequentially. If a price level accumulates `min_volume` on *both* sides simultaneously (possible at a highly contested level), the sell-absorption branch fires first, calls `_reset_level`, and the buy-absorption check on the next call starts from zero. The implicit priority (sellers-absorbed → LONG fires before buyers-absorbed → SHORT) is undocumented and could produce confusing signal sequences at levels with heavy two-way flow.
