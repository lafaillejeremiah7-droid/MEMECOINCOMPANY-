# NQ order flow signal bot — v2 review (all prior issues addressed)

The five issues from v1 are resolved: aggressor side is now classified by comparing trade price to bid/ask, the forward-results loop implements the full update logic, bars close every 5 seconds (configurable), the reconnection `ensure_future` is wrapped in `try/except RuntimeError`, and absorption priority is documented in the class docstring. The package (14 modules, ~5,400 lines, 98 tests passing) is in substantially better shape for production use.

**Watch for:** The `_on_tick` callback fires `asyncio.ensure_future` for signal processing but never stores or awaits the resulting future, meaning exceptions in `_process_tick_signals` are silently dropped unless the event loop's exception handler is configured (confirmed). Forward results for signals that cross multiple interval thresholds in a single poll iteration (e.g., after a bot restart) collapse all intervals to the same current price, losing timing granularity (confirmed).

**Verdict**: APPROVED

## High-level view

The forward-results loop progressively fills price columns using `COALESCE` in the UPDATE so earlier-recorded values are not overwritten, and signals exit the query once `price_1h` is set. The design works correctly under continuous operation but collapses timeframes for signals that age past multiple thresholds before their first poll (detailed below).

The remaining architectural rough edge is error observability in the tick path: the async signal-processing pipeline spawned per tick has no done-callback, so exceptions in database writes or Telegram sends during signal emission are silently lost in a long-running process.

## Fire-and-forget futures in the tick path

In `main.py`, the `_on_tick` callback (invoked synchronously from ib_insync's `pendingTickersEvent`) spawns an async coroutine for signal processing:

```python
asyncio.ensure_future(
    self._process_tick_signals(
        price, volume, is_ask, timestamp,
        large_print, absorption_signal
    )
)
```

The returned `Task` is discarded. If `_process_tick_signals` raises—database timeout, Telegram send failure that propagates, a `KeyError` in signal metadata—the exception goes to the event loop's default handler, which typically prints a warning to stderr and continues. In a long-running process with rotating logs, this can mean silent signal loss with no indication in the structured log.

The outer `_on_tick` has a try/except that catches synchronous errors (delta update, volume profile update, etc.), but the async tail is outside that scope. The simplest fix:

```python
task = asyncio.ensure_future(self._process_tick_signals(...))
task.add_done_callback(self._handle_task_exception)
```

Where `_handle_task_exception` checks `task.exception()` and logs at ERROR level.

## Forward-result timing collapse on first fill

The `_check_forward_results` loop runs every ~1 second. For each incomplete signal, it checks elapsed time and sets all intervals that have passed:

```python
if elapsed >= 300:
    price_5m = current_price
if elapsed >= 900:
    price_15m = current_price
if elapsed >= 1800:
    price_30m = current_price
if elapsed >= 3600:
    price_1h = current_price
```

If a signal was emitted 65 minutes ago and this is the first time the loop encounters it (fresh bot start, or the signal was emitted just before a brief disconnection), all four fields get the same `current_price`. The `COALESCE` in the UPDATE prevents overwriting *existing* non-NULL values, so subsequent polls are safe—but the initial write for a long-pending signal collapses all four timeframes into a single observation.

This is non-blocking because: (a) under normal continuous operation, signals are filled incrementally every second; (b) after a restart, the adaptation engine seeing identical prices across intervals is slightly inaccurate but not systematically biased in either WIN or LOSS direction.
