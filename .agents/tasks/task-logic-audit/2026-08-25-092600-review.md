# Six logic bug fixes for signal quality and P&L accuracy (v2)

This is the second review pass. The first pass identified two issues: the partial-close INSERT stored the post-mutation `tokens_held` (20% residual instead of the sold 80%), and a dead `usd_sign` variable. Both have been resolved in the latest commit.

The change set resolves six correctness issues: trailing stop anchoring to original entry, fresh unrealized P&L in portfolio summaries, partial take-profit persistence, common-funder docstring alignment, RecoveryChecker dependency injection, and `__main__.py` wiring of configured instances. The approach is conservative — all new constructor parameters are optional with env-based defaults, preserving backward compatibility for existing callers and tests.

Watch for: No blocking concerns remain. The partial-close INSERT now stores the correct sold token count and all P&L arithmetic is internally consistent across DCA, take-profit, and trailing-stop paths.

**Verdict**: APPROVED

## High-level view

The trailing stop and hard stop are now both anchored to `original_entry_price`, eliminating the asymmetry where a DCA lowered the trailing stop threshold without the trader's intent. After a DCA that rebases `entry_price` to the weighted average cost, the trailing stop triggers at the *original* entry (higher than the DCA-adjusted entry), protecting more profit on the remaining 20%.

The portfolio summary computes unrealized P&L inline from `current_price` vs `entry_price` at display time, removing the dependency on the `unrealized_pnl` field which was only refreshed during `check_positions` cycles.

The partial-close INSERT now writes a `'partial_closed'` row with correct `sold_tokens` (computed before the mutation) and `sold_amount`, ensuring that the 80% take-profit record survives process restarts and contributes accurately to daily/lifetime P&L summaries.

RecoveryChecker accepts pre-configured `OnchainAnalyzer` and `XSearchClient` instances from the caller, eliminating the silent env-var fallback that would produce degraded recovery checks (biased toward SELL) when API keys are only in YAML config.

## Partial-close token count fix

```python
sold_tokens = pos["tokens_held"] * TAKE_PROFIT_SELL_FRACTION  # computed before mutation
pos["tokens_held"] = pos["tokens_held"] * (1.0 - TAKE_PROFIT_SELL_FRACTION)
```

The v1 bug had `pos["tokens_held"]` read after the reduction, storing 20% of original in a row meant to represent the 80% sold. The fix captures `sold_tokens` on the line immediately before the mutation. The INSERT tuple passes `sold_tokens` alongside `sold_amount` (80% of USD), preserving the invariant `sold_amount / sold_tokens == entry_price`.

## Portfolio summary staleness window

The summary uses `p.get("current_price", ep)` — if called before the first `check_positions` cycle after restart, `current_price` equals `entry_price` from the DB load, producing $0 unrealized. This is pre-existing and benign: the portfolio timer (3600s) fires well after the first check cycle (300s) in normal operation.
