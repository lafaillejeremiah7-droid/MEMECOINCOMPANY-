# Six logic bug fixes for signal quality and P&L accuracy

This commit resolves six distinct correctness issues across the paper trading pipeline: trailing stop anchoring to pre-DCA entry, fresh unrealized P&L computation in portfolio summaries, persistence of partial take-profit records, docstring alignment for common-funder detection, dependency injection for RecoveryChecker, and wiring configured instances through `__main__.py`. The fixes are narrowly scoped and individually reasonable, though one introduces a new data integrity issue in the partial-close INSERT.

Watch for: The partial-close INSERT persists the *remaining* 20% token count instead of the *sold* 80% token count (confirmed). The portfolio summary's fresh P&L computation uses `entry_price` (DCA-adjusted) rather than `original_entry_price`, which is intentional for display but creates a subtle inconsistency with how stop-losses are anchored (likely cosmetic, not a trading logic error).

**Verdict**: NEEDS_CHANGES

## High-level view

The trailing stop fix correctly anchors the breakeven trigger to `original_entry_price`, ensuring a DCA that lowers cost basis doesn't silently loosen the trailing stop threshold. The hard stop at -70% was already using the original entry for its percentage calculation, so trailing and hard stops are now consistently anchored.

The portfolio summary now computes P&L at display time from `current_price` vs `entry_price` instead of reading the `unrealized_pnl` field, which is only refreshed during `check_positions` cycles. Both use the DCA-adjusted `entry_price`, which is correct for reporting cost-basis-relative returns to the user.

The partial-close persistence ensures take-profit records survive a bot restart, but the INSERT row stores incorrect `tokens_held` — it records the post-reduction residual rather than the tokens actually sold. This affects historical accuracy and any downstream analytics that compute average exit price from `amount_usd / tokens_held`.

RecoveryChecker dependency injection eliminates a long-standing issue where each `check_positions` cycle instantiated unconfigured `OnchainAnalyzer` and `XSearchClient` objects that lacked the API keys and RPC endpoints configured at startup. The `__main__.py` wiring completes the plumbing.

The common-funder docstring fix aligns documentation with existing code behavior — the detection logic already triggered at 2+ shared sources; only the comment was wrong.

## Partial-close INSERT has wrong tokens_held

```python
pos["tokens_held"] = pos["tokens_held"] * (1.0 - TAKE_PROFIT_SELL_FRACTION)  # reduces to 20%
# ... later in the INSERT:
sold_amount, pos["tokens_held"],  # tokens_held already reduced ← comment acknowledges it, but value is wrong
```

The intent of the `partial_closed` row is to record what was *sold*. `sold_amount` correctly represents 80% of USD, but `tokens_held` at this point represents 20% of the original tokens — the residual, not the sold portion. The row should persist `original_tokens_held * TAKE_PROFIT_SELL_FRACTION`.

Fix: capture `sold_tokens = pos["tokens_held"] * TAKE_PROFIT_SELL_FRACTION` *before* the mutation line (around line 637), then pass `sold_tokens` to the INSERT instead of `pos["tokens_held"]`.

Impact: any analytics query computing average exit price as `amount_usd / tokens_held` from `partial_closed` rows gets an inflated value (4× actual, since it divides 80% USD by 20% tokens). The live P&L tracking is unaffected because `pnl_usd` and `pnl_pct` are computed independently from the percentage gain, but the stored row is internally inconsistent and will corrupt calibration reports or win-rate analytics that rely on token quantities.
