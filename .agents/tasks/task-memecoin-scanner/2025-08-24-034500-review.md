# Signal-only Solana memecoin scanner with 6-factor scoring engine

This adds a complete async Python bot that scans Pump.fun and DEXScreener for newly launched Solana tokens, scores them on a 6-factor weighted system (buy/sell ratio, liquidity, volume turnover, engagement velocity, narrative match, momentum), calculates probability estimates and expected value, and sends Telegram alerts for tokens exceeding the configured threshold. A background adaptation engine tracks alerted token outcomes at 1h/6h/24h intervals and reweights scoring factors based on actual performance. The implementation is signal-only — no wallet keys, no transaction construction, no trade execution anywhere in the codebase.

Watch for: The in-memory `_seen_mints` set grows unbounded for the lifetime of the process (confirmed). The `narrative_hit_rates` accumulation in `generate_weekly_stats` has a type annotation bug — it's annotated `Dict[str, float]` but accumulates lists (confirmed). The database's `INSERT OR REPLACE` in `insert_token` will clobber outcome data if a token is ever re-inserted (confirmed). The DEXScreener rate limiter has a potential race between concurrent async tasks sharing the same client instance (likely).

**Verdict**: APPROVED

## High-level view

The scoring engine implements the exact weights from the spec (25/25/20/15/10/5) with discrete threshold bands per factor rather than continuous curves. Each factor scores 0/25/50/75/100 based on where the raw metric falls, and the weighted sum produces a 0–100 composite. The thresholds are hardcoded but the weights are adjustable via self-adaptation after 50 tracked samples.

Hard filters run before DEXScreener is queried (flagged/banned, dev holdings) and again after (liquidity, buy/sell ratio, dump detection), saving API calls for obviously bad tokens. The dev-holdings check estimates wallet concentration from `total_supply - real_token_reserves`, which conflates early buyers with dev allocations and will miss multi-wallet rug setups.

The main loop orchestrates three concurrent background tasks sharing a single `DexScreenerClient` instance. The rate limiter uses a bare `time.time()` field without an asyncio lock, so two tasks checking the rate limit simultaneously could both pass and fire requests within the delay window.

The probability calculator converts the 0–100 score into a step-function multiplier (0.2x/0.5x/1x/2x/3.5x) applied to research base rates. EV calculation blends gains across 100k, 300k, and 1M targets with weighting factors of 1.0, 0.3, and 0.1 respectively.

The adaptation engine's `_compute_correlations` uses a simple hit-rate metric (what fraction of tokens with factor score ≥50 had positive outcomes) rather than actual statistical correlation. Weight adjustment is conservative — 10% max change per cycle, bounded below at 0.02, then renormalized.

The Telegram bot token is loaded from plaintext YAML with no environment-variable override or secret-management integration.

## Unbounded `_seen_mints` growth

The `MemeScanner` class tracks seen mints in `self._seen_mints: Set[str]`. Every processed mint is added but never removed. Pump.fun sees thousands of tokens per day; over days or weeks this set will consume meaningful memory on low-spec VPS instances where this kind of bot typically runs.

The set serves as a performance optimization — the real deduplication guard is `self.database.token_exists(mint)` which correctly prevents re-alerting. But the unbounded growth means the process's memory footprint increases linearly with uptime.

## `INSERT OR REPLACE` clobbers tracked outcome data

In `database.py`, `insert_token` uses:

```sql
INSERT OR REPLACE INTO tokens
    (mint, name, symbol, first_seen, score, features_json, alerted,
     alerted_at, market_cap_at_alert)
VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?)
```

This replaces the entire row on conflict. The `outcome_1h`, `outcome_6h`, `outcome_24h` columns — not included in the INSERT — will be set to NULL, destroying adaptation data. Currently protected by the `token_exists` check in the scan loop, but this is fragile: `adaptation.py`'s `log_alert` also calls `insert_token`, creating a second INSERT for already-stored tokens. If a token was stored by the scan loop (with `alerted=0`) and then scores above threshold, `log_alert` re-inserts it with `alerted=1`, which would overwrite any data the scan-loop INSERT recorded.

## Rate-limit race on shared `DexScreenerClient`

Both the scan loop and the outcome-check loop share the same `dex_client` instance:

```python
async with DexScreenerClient() as dex_client:
    tasks = [
        asyncio.create_task(self._scan_loop(pump_client, dex_client, telegram)),
        asyncio.create_task(self._outcome_check_loop(dex_client)),
    ]
```

The rate limiter in `_rate_limit()`:

```python
now = time.time()
elapsed = now - self._last_request_time
if elapsed < self.rate_limit_delay:
    await asyncio.sleep(self.rate_limit_delay - elapsed)
self._last_request_time = time.time()
```

Two coroutines can read `_last_request_time` at the same instant, both conclude that enough time has passed, and both fire requests without sleeping. Wrapping this in an `asyncio.Lock` would serialize access.

## Type annotation inconsistency in weekly stats

In `adaptation.py`, `narrative_hit_rates` is declared:

```python
narrative_hit_rates: Dict[str, float] = {}
```

But populated with:

```python
narrative_hit_rates[kw] = []
narrative_hit_rates[kw].append(1 if outcome > 0 else 0)
```

The actual type is `Dict[str, List[int]]`. Static analysis tools (mypy, pyright) would flag this, and the inconsistency could mislead future maintainers.

## Dev-holdings filter limitations

The `_check_dev_holdings` method calculates:

```python
tokens_in_wallets = total_supply - real_token_reserves
wallet_pct = (tokens_in_wallets / total_supply) * 100
```

This treats all tokens not in the bonding curve as "dev holdings," which conflates early buyers, team allocations, and normal holders. The filter will miss multi-wallet rugs where the dev distributes supply across wallets each holding below 50%.

## Test coverage gaps

Not tested: the main loop orchestration (`main.py`), the adaptation engine's full workflow, the Telegram bot's message formatting and sending, database operations, and the API clients' error handling and rate limiting. The glue code between modules is only exercised in production.
