# NAS100 signal-only bot with edge detection, Kelly criterion, and Telegram alerts

This change builds a complete signal-only trading bot for NAS100 from scratch. The bot fetches market data via yfinance, evaluates ten statistically-derived edge functions (six long, four short), scores confluence, computes Kelly-optimal sizing suggestions, and delivers alerts through Telegram. The architecture is modular (config, data, edges, signals, kelly, timing, scheduler, telegram) with a scheduler that runs checks at configured times during market hours. A 122-test suite covers edge detection, Kelly math, signal generation, and timing logic.

Watch for: the data layer has a shared-cache design that silently serves stale hourly data for the "first candle" edge across check intervals (confirmed); the Telegram sender's async-to-sync bridge uses a ThreadPoolExecutor with no timeout control beyond the thread's internal 30-second hard cap, meaning a stuck Telegram call blocks a scheduler slot indefinitely (confirmed); the Kelly formula uses a custom variant (`(WR*W - LR*L) / W`) that can yield fractions above 1.0 for high-WR edges yet the only cap is `max_kelly_fraction` applied multiplicatively rather than as a ceiling (confirmed).

**Verdict**: APPROVED

## High-level view

The data layer introduces a simple time-based cache shared between daily and hourly fetches. Because both caches share a single `_cache_time` timestamp, fetching daily data resets the hourly cache timer, which can cause the first-candle edge to evaluate against a stale hourly bar from a prior check cycle.

Edge functions are pure-ish computations that accept pre-computed market state and return dictionaries with hard-coded research statistics. The design keeps detection logic simple and testable, but it also means the bot's statistical claims (win rates, sample sizes) are compile-time constants that drift from reality as new market data accumulates.

Signal generation resolves conflicting directions by count—if three long edges and two short edges fire simultaneously, the long side wins. There is no cancellation logic or explicit handling of the scenario where both sides are strongly supported; the minority edges are discarded silently rather than surfaced as a mixed-signal warning.

The Kelly module correctly implements the formula and applies a configurable fraction cap, but because the cap is multiplicative (`kelly * max_fraction`) rather than a min-clamp, edge combinations with very high weighted win rates can still suggest risk percentages above 50% of account, which may surprise users expecting the cap to be an absolute ceiling.

The scheduler uses the `schedule` library's synchronous polling loop with a 1-second sleep. Each check runs inline in the main thread with no timeout. A slow yfinance fetch or a stuck Telegram call blocks all subsequent scheduled checks until it completes or times out.

Telegram integration handles the common async-event-loop pitfalls (running loop detection, fallback to `asyncio.run`) but the ThreadPoolExecutor fallback path creates a new thread pool per call with no cleanup guarantee if the send hangs past the 30-second `future.result` timeout.

<summary>Issues (7)</summary>

1. **Shared cache timer serves stale hourly data** — `_cache_time` is shared between daily and hourly caches; a daily fetch resets the timer and causes subsequent hourly reads to return stale data. Give each cache its own timestamp.
2. **No timeout on yfinance fetches** — A hung HTTP call in `fetch_daily` or `fetch_hourly` blocks the scheduler's main thread indefinitely. Wrap yfinance calls in a timeout or run them in a thread with a deadline.
3. **Kelly cap is multiplicative, not a ceiling** — `min(kelly * max_fraction, kelly)` simplifies to `kelly * max_fraction` for all positive kelly values. If the intended behavior is "never suggest more than 50% of account," it should be `min(kelly, max_fraction)`.
4. **Conflicting edges discarded without warning** — When long and short edges fire simultaneously, the minority direction is silently dropped. A mixed-signal warning in the log or alert would prevent blind spots.
5. **Telegram send blocks scheduler** — `send_signal` runs synchronously in the check callback. A slow Telegram API call (network issue, rate limit) blocks the scheduler loop. Send asynchronously or move alerting to a separate thread/queue.
6. **Static research statistics will drift** — Win rates, avg win/loss, and sample sizes are hard-coded constants. Over time they'll diverge from actual performance. Consider adding a note or versioning scheme for when these should be re-validated.
7. **No market-holiday awareness** — `is_market_day` checks weekday only. Trading on NYSE holidays (e.g., MLK Day, Good Friday) will produce spurious signals against illiquid pre/post-market data or simply fail to fetch data.

## Data layer cache design

`MarketData` uses a single `_cache_time` timestamp shared between daily and hourly caches. The validity check (`_is_cache_valid`) returns True for *both* caches if *either* fetch happened within `cache_minutes`:

```python
def _is_cache_valid(self) -> bool:
    if self._cache_time is None:
        return False
    elapsed = (datetime.now() - self._cache_time).total_seconds() / 60
    return elapsed < self.cache_minutes
```

In `run_check`, daily data is fetched first, which sets `_cache_time`. The subsequent hourly fetch sees the cache as valid and returns potentially stale hourly data from the previous cycle. The first-candle edge depends on fresh hourly data to detect the >0.3% move, so a stale cache means the signal evaluates against the *previous* check's first candle. With the default 5-minute cache and 60-minute check intervals, this only matters if the scheduler fires twice within 5 minutes (unlikely with current config), but reducing `data_cache_minutes` or adding more frequent checks would expose the bug immediately.

Neither `fetch_daily` nor `fetch_hourly` applies any timeout to the yfinance HTTP call. If the yfinance backend hangs (rate-limited, network partition), the entire scheduler loop blocks on the socket read. The `schedule` library is single-threaded by design, so no other checks will fire until the hung call either completes or the OS TCP timeout kicks in (often 2+ minutes).

## Kelly formula cap semantics

In `calculate_kelly`:

```python
capped_kelly = min(kelly_fraction * max_kelly_fraction, kelly_fraction)
```

For any `max_kelly_fraction` in (0, 1] and positive `kelly_fraction`, `kelly_fraction * max_kelly_fraction` is always less than or equal to `kelly_fraction`, so the `min()` always resolves to `kelly_fraction * max_kelly_fraction`. This is equivalent to just `kelly_fraction * max_kelly_fraction` without the min call. At the default 0.5 this yields half-Kelly, which is a common conservative approach.

However, consider an edge combination yielding `kelly_fraction = 1.2` (possible when weighted win rate is very high and avg_loss is low relative to avg_win). The suggested risk would be `1.2 * 0.5 = 0.6`, i.e., 60% of account. If the intent is "never suggest more than 50% of account regardless of Kelly output," the formula should be `min(kelly_fraction * max_kelly_fraction, max_kelly_fraction)` or simply `min(half_kelly, some_absolute_cap)`. The current behavior is mathematically consistent with fractional-Kelly but may surprise users who interpret `max_kelly_fraction: 0.5` as "never more than 50%."

## Signal direction resolution and mixed signals

`generate_signal` picks direction purely by count:

```python
if long_score >= short_score:
    direction = "LONG"
    active_edges = triggered_long
else:
    direction = "SHORT"
    active_edges = triggered_short
```

A scenario like "first 1H candle bearish" (84.8% WR, 178 samples) firing alongside "RSI oversold" (70.1% WR, 144 samples) + "5 red days bounce" (63.4% WR, 41 samples) produces a LONG signal that ignores a strong short edge. The long side wins on count (2 vs 1) despite the short edge having higher individual win rate and more samples. The discarded short edge is never logged or surfaced to the user, which could create a blind spot in mixed-regime markets.

## Scheduler single-thread blocking

The scheduler loop is a tight `while True: schedule.run_pending(); time.sleep(1)`. Each check runs the full pipeline synchronously: fetch → evaluate → Kelly → format → Telegram send. The Telegram path in particular uses a ThreadPoolExecutor with `future.result(timeout=30)`:

```python
with concurrent.futures.ThreadPoolExecutor() as pool:
    future = pool.submit(asyncio.run, send_signal_async(signal, config))
    return future.result(timeout=30)
```

If the 30-second timeout fires, a `TimeoutError` propagates up, but the *thread* running `asyncio.run` is not cancelled — the `with` block waits for the executor to shut down, which waits for the thread to finish. This effectively turns the 30-second timeout into a no-op when the Telegram call is truly stuck, because `ThreadPoolExecutor.__exit__` calls `shutdown(wait=True)`.

## Test coverage gaps

The test suite covers edge detection logic, Kelly math, signal generation with mocked edges, and timing utilities. Areas not tested:

- `MarketData` integration (yfinance fetch, cache behavior, timezone conversion of hourly data)
- `run_check` orchestration (the main loop that ties data → edges → signal → alert)
- Telegram sending (the async wrapper, HTML formatting rendering)
- Scheduler behavior (market-day filtering, error recovery, stop/restart)
- Config validation error paths (malformed YAML, type mismatches)

The test fixtures use synthetic data that exercises both triggered and non-triggered paths for every edge, and the Kelly tests verify mathematical correctness with known values, which is appropriate for a greenfield project. The missing integration coverage is a natural second-phase concern.
